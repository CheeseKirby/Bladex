# 架构说明

## 1. 系统边界

Bladex 的 Harness 层贯穿方案设计与代码生成，而不是某一个独立服务。它把 BladeX 规范、参考项目上下文和模型调用接入同一套工程流程：以统一领域契约传递已确认的设计，用审核凭证约束阶段流转，按交付物及其依赖组织生成，再通过跨文件校验、确定性修复和隔离输出检查并保存结果。持久化状态、执行日志与产物报告为后续恢复和问题追踪提供依据。

这样的分工让模型承担需求理解和内容生成，将契约一致性、执行边界与结果验收交给可检查的程序机制。Harness 并不意味着生成代码天然正确：内置源码门禁只覆盖依赖无关的检查，完整可编译性仍需在目标项目的真实依赖环境中验证。

项目由三个进程组成：

1. `ai-designer/src`：React 可视化设计端。
2. `ai-designer/server`：Part A / BFF，负责需求扩充、方案生成、审核、拆分、持久化和传输。
3. `ai-developer/ai-workflow`：Part B，负责契约接收、原子任务编译、代码生成、质量修复、文件持久化和执行时间线。

默认端口分别为 3005、3004 和 8111。生成结果默认写入仓库外观隔离目录 `ai-generated-modules/`，不会直接修改参考项目。

## 2. Canonical Plan Contract v2

新版链路以版本化领域契约作为跨阶段唯一事实来源。契约包含：

- 模块、实体、表、基础包和服务身份；
- 持久化字段、派生字段、Java/SQL 类型及来源证据；
- 状态、集成、参考绑定和架构决策；
- 稳定交付物 ID、物理模块、依赖和类型提供/消费关系；
- 契约版本、内容哈希、参考快照和规则集版本。

Part A 和 Part B 使用 `contracts/fixtures/` 中的共享 fixture 校验结构哈希和签名，避免跨语言模型漂移。

## 3. 审核与拆分

审核记录持久化 `reviewId`、内容哈希、契约哈希、参考快照、规则版本、模型轮次和最终问题。拆分接口必须携带有效审核凭证；方案内容变化后旧凭证失效。

拆分只组织交付物边界和依赖顺序，不允许新增契约外模块、实体、字段、类型或交付物。每个子方案携带 `deliverableIds`、`contractHash`、输入/输出类型和引用元素 ID。

## 4. Part B 生成与质量闭环

Part B v2 直接消费统一契约：

1. 校验 Schema、bundle 哈希、HMAC 签名和审核清单。
2. 将交付物编译为原子任务并检查 DAG、所有权和类型闭包。
3. 在隔离目录生成代码。
4. 执行文件级、跨文件、领域契约、DDL/Entity、Mapper/XML、Controller/Service 和源码门禁校验。
5. 只对可机械推导的问题执行确定性修复；候选没有减少错误或引入新错误时立即拒绝。
6. 从最终持久化文件重新计算报告、manifest 和执行状态。

历史 Markdown 请求只保留隔离兼容路径；新版请求不会静默降级。

## 5. 持久化与恢复

- Part A 项目状态和审核记录使用原子 JSON 文件持久化。
- Part B 使用 MySQL 保存方案、子方案、执行日志和生成文件。
- 完成的审核和执行记录可在进程重启后恢复。
- 中断记录会进入明确的可重试状态，不以不确定的“卡住”状态继续。

## 6. 安全边界

- `.env`、模型 token、数据库密码和 bundle 签名密钥不得提交。
- BFF 和 Part B 默认绑定回环地址；非回环访问必须配置管理 token 和可信网络边界。
- 默认写入目标为 `ISOLATED`；真实项目写入必须显式授权。
- 参考项目只用于扫描、绑定和验证，不应由日常生成流程直接修改。
